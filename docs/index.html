local-llms Documentation

The local-llms repository is a Ploinky-managed collection of twelve agents that run local large language models as MCP servers. All agents share a single Docker image (assistos/local-llms), a common set of runtime scripts, a declarative model catalog, and a shell-based MCP dispatcher. The system provides a Ploinky workspace with self-hosted inference across translation, relevance scoring, function routing, general chat at multiple parameter scales, planning, and agentic coding.

Coding style and test organization are defined in DS001 Coding Style. The full specification set is available in the Specification Matrix.

Architecture

The system consists of three layers: the shared Docker image (which contains all backend binaries, Python services, and runtime scripts), the per-agent directories (which contain Ploinky manifests, MCP configurations, and healthcheck wrappers), and the shared volume mount (which holds model weights, the dynamic registry, and generated startup scripts).

When Ploinky starts an agent, it mounts the agent directory at /code and the shared volume at /data/local-llms. The manifest's start command points to /opt/local-llms/scripts/start-agent.sh inside the image, which orchestrates backend startup, readiness polling, optional model pull, and AgentServer handoff.

Agents

The repository defines twelve agents with distinct roles. The manager agent (local-llms-manager) handles model registration, startup script generation, and profile lifecycle without running any model backend. The eleven model-serving agents each run a specific backend and expose MCP tools for model lifecycle operations.

At default startup, the manager enables function-selection and function-invocation with no-wait, so the manager becomes MCP-ready immediately while the two model agents load their backends in the background. All other agents must be explicitly enabled by the operator.

Each backend represents a model serving technology with its own port, API shape, readiness probe, and storage path. The backend definitions live in catalog/backends.json.

Seq2seq translation models and cross-encoder rerankers cannot run through Ollama or llama.cpp because they require encoder-decoder or cross-encoder architectures. The catalog enforces that these models are routed to their specialized Python backends.

Catalog System

The catalog is the declarative source of truth for backend definitions and per-agent model assignments. It lives under catalog/ in the repository and is copied to /opt/local-llms/catalog in the Docker image. JSON Schema files under catalog/schemas/ define the required structure.

Each agent catalog entry declares its supported models, default model, backend, RAM band, CPU safety, and readiness timeout. Models can include a backendModel field to map a user-facing identifier to a backend-specific name (e.g., google/translategemma-4b-it maps to translategemma:4b for Ollama).

MCP Dispatcher

The dispatcher (scripts/dispatcher.sh) is the single entry point for all MCP tool calls. Every agent's mcp-config.json routes tool invocations to this script with a TOOL_NAME environment variable. The dispatcher handles AgentServer envelope unwrapping (four formats), input validation via slug and model-name character sets, backend-model alias resolution, and registry management.

The manager exposes six tools (list, register, generate script, register profile, promote, status). Model agents expose five tools (list, start, stop, status, register). Translation and relevance agents add specialized translate and rerank tools respectively.

Runtime Scripts

The startup pipeline is sequential: start-agent.sh checks resources, launches the backend runner, polls readiness, optionally pulls the default model, then hands off to AgentServer. Each backend runner is a thin shell wrapper that configures environment and execs the backend process.

The healthcheck script routes probes based on agent identity: AgentServer /health for the manager, ollama list for Ollama agents, and /health HTTP probe for all others.

Python Services

Two agents use Python Flask services instead of Ollama or llama.cpp:

Translation service (translation_service.py) loads a HuggingFace seq2seq model via transformers.pipeline("translation"). The default is facebook/m2m100_418M (418M parameters, 100 languages). The /health endpoint returns 503 until the model is loaded. Translation requests go to POST /translate with text, source language, and target language.

Reranker service (reranker_service.py) loads a cross-encoder via sentence_transformers.CrossEncoder. The default is Qwen/Qwen3-Reranker-0.6B (0.6B parameters, 100+ languages, 32k context). Reranking requests go to POST /rerank with query, passages, optional top-k, and optional instruction prefix.

Storage Layout

All agents share a single volume mount (.ploinky/data/local-llms on the host, /data/local-llms in the container). Model storage is organized by backend to prevent naming conflicts while enabling cross-agent sharing. The dynamic registry and generated startup scripts also live under this root.

Model weights are never baked into the Docker image. Ollama models are pulled at first start or via start_model. HuggingFace models are cached on first service startup. llama.cpp GGUF files must be pre-placed by the operator.

GPU and Resource Policy

The startup script enforces a RAM floor check by parsing the lower bound of the catalog ramBand and comparing it against /proc/meminfo. Agents marked cpuSafe: false (adaptive-local, coding-local) trigger a warning when no NVIDIA GPU signal is detected, but startup continues because Ploinky manifests do not model GPU passthrough.

GPU access requires operator-level Docker/Podman flags (--gpus all or --device nvidia.com/gpu=all). See DS010 GPU and Resource Policy for details.

Testing

The test suite runs with node --test tests/validate.mjs and validates 123 structural and behavioral contracts without requiring Docker or model downloads. Tests cover catalog validity, manifest contracts, MCP config structure, tool surface separation, backend routing rules, default startup behavior, port ordering, dispatcher envelope handling, path traversal rejection, and Python service properties. See DS011 Testing Strategy for coverage details and known gaps.
