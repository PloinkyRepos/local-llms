# Local LLM Ploinky Agents - Revised Plan

## Summary

Bootstrap `local-llms` as a Ploinky repo with first-class Ploinky agents for the requested local LLM roles. Treat Ollama, llama.cpp, and LM Studio as suggested runners, not a closed set. Keep one shared `assistos/local-llms:<tag>` image for v1, but make backend support explicit and realistic:

- `ollama` for Ollama-native chat/tool models.
- `llama_cpp` for GGUF-backed llama.cpp server models.
- `vllm` or `sglang` for HuggingFace causal/chat models where an OpenAI-compatible server is a better fit than Ollama.
- `transformers_seq2seq` for HuggingFace encoder-decoder/text-to-text translation models.
- `reranker` for cross-encoder or sentence-transformers ranking models with a scoring API.
- `lmstudio_llmster` is optional/experimental: LM Studio now has a headless daemon, but the repo should not depend on it as a core v1 runner until install, licensing, Docker, and GPU behavior are verified in the target image.

Use a hybrid config model:

- Repo catalog for committed agents, model candidates, backend family, RAM/GPU guidance, ports, readiness, and startup presets.
- Workspace registry under `.ploinky/data/local-llms` for runtime model registrations, generated scripts, downloaded-model metadata, and operator overrides.
- Default startup enables `local-llms-manager` plus `function-selection` and `function-invocation` using `no-wait` dependency edges.

## Implementation Changes

### Repo And Agent Layout

- Keep the original plan as historical context and implement from this v2 plan.
- Add top-level agent folders:
  - `local-llms-manager`
  - `language-translation`
  - `relevance`
  - `function-selection`
  - `function-invocation`
  - `tool-composition-local`
  - `base-local`
  - `local`
  - `planning-local`
  - `validated-planning-local`
  - `adaptive-local`
  - `coding-local`
- Each folder gets a `manifest.json` and `mcp-config.json`.
- Every manifest includes `about`, `profiles.default`, explicit env defaults, declared ports, and readiness configuration.
- The manager manifest uses `enable[]` entries with `no-wait` for the light defaults:
  - `function-selection global no-wait`
  - `function-invocation global no-wait`

### Shared Image And Backends

- Add one shared `Dockerfile` based on Node 24 + Debian slim with Python 3, curl/git/build tools, Ollama, llama.cpp server, and Python dependencies needed for lightweight `transformers` serving.
- Add Python dependencies for small HTTP services that wrap `transformers`, `sentence-transformers`, and backend-specific health/status probes.
- Include vLLM/SGLang only if image size and CUDA/CPU compatibility remain acceptable; otherwise make them installable backend profiles generated by the manager.
- Do not make LM Studio/llmster a default v1 backend. Add it as `experimental: true` if the implementation can install or call the official headless daemon without the desktop app.
- Backend runners live under `scripts/runners/`:
  - `ollama.sh`
  - `llama-cpp.sh`
  - `vllm.sh`
  - `sglang.sh`
  - `transformers-seq2seq.sh`
  - `reranker.sh`
  - `lmstudio-llmster.sh` (experimental)
- `scripts/start-agent.sh` reads `LOCAL_LLMS_AGENT_ID`, resolves merged config, starts the chosen backend on a known container-local port, waits for backend readiness when needed, then starts Ploinky `AgentServer`.

### Catalog And Runtime State

- Add `catalog/backends.json` with backend definitions, internal ports, readiness probes, API shape, and model storage paths.
- Add `catalog/agents/<agent>.json` for every role, with:
  - model candidates
  - backend family per model and task API shape
  - default model
  - RAM band and minimum recommended GPU/VRAM metadata
  - startup preset
  - whether it is default-enabled
  - readiness timeout policy
- Runtime state lives under `.ploinky/data/local-llms`:
  - `registry.json` for dynamic model/profile registrations
  - `scripts/<profile-id>/start.sh` for generated startup scripts
  - `ollama/` shared Ollama root
  - `llama-cpp/models/` shared GGUF cache
  - `transformers/cache/` shared HuggingFace cache
  - `agents/<agent-id>/` per-agent runtime scratch

### Initial Model Routing Audit

- `facebook/m2m100_418M`: use `transformers_seq2seq`; this is an encoder-decoder translation model, not a chat-completion model.
- `google/madlad400-3b-mt`: use `transformers_seq2seq` by default; llama.cpp/T5 GGUF support can be tested later, but the safe v1 API is text-to-text translation.
- `utter-project/EuroLLM-1.7B-Instruct`: use `vllm`, `sglang`, `llama_cpp`, or Ollama if a verified quantization exists; it is a causal instruction model and can serve chat/text generation.
- `google/translategemma-4b-it`: use Ollama `translategemma` or vLLM/SGLang with the required translation chat template; expose a translation MCP tool rather than pretending every call is generic chat.
- `Qwen/Qwen3-Reranker-0.6B`: use `reranker`; expose scoring/reranking MCP tools, not `/v1/chat/completions`.
- `functiongemma`: use Ollama with a minimum Ollama version check.
- `qwen3.5`, `qwen3.6`, `granite4.1`, `hermes3`, `phi4-mini`, `ministral-3`, and `gemma4` candidates are Ollama-compatible as catalog entries, with per-model minimum Ollama version constraints where the library declares them.

### MCP Tools

- Manager `mcp-config.json` exposes management tools:
  - `list_available_models`
  - `register_model`
  - `generate_startup_script`
  - `register_agent_profile`
  - `promote_agent_profile`
  - `status_model`
- Model-agent `mcp-config.json` exposes model lifecycle tools only:
  - `list_available_models`
  - `start_model`
  - `stop_model`
  - `status_model`
  - `register_model` only if scoped to that agent's workspace registry entries.
- All tools call a shared dispatcher script, but each agent owns its own `mcp-config.json` because AgentServer resolves config from `/code/mcp-config.json`.

### Model Download And Readiness

- Add explicit `pull_model`/`download_model` behavior inside `register_model` or as a separate internal dispatcher action.
- Default behavior:
  - Do not pre-bake model weights into the Docker image.
  - Do not pull all candidate models during startup.
  - Pull/download only the configured default model for default-enabled agents, through a manifest `postinstall` hook or first-start bootstrap script with extended readiness.
  - Additional models are downloaded by explicit MCP tool calls.
- Model-serving agents must not let AgentServer report healthy while their selected backend/default model is unusable. `start-agent.sh` should start the backend, run the backend/model readiness probe, then launch AgentServer.
- Ploinky startup readiness currently gates only TCP/MCP on a host-side route port. Manifest `health.readiness.script` is useful for container monitoring, but it is not enough by itself for dependency-wave gating.
- Manager readiness is MCP-only and should become ready without waiting for no-wait dependencies.

### Ports And Endpoints

- Each model-serving container runs:
  - AgentServer on internal port `7000`.
  - Backend service on a backend-specific internal port, for example Ollama `11434`, llama.cpp `8080`, transformers service `8090`.
- Agent manifests declare ports needed by Ploinky readiness and routing. When the Ploinky route should target AgentServer/MCP, the `7000` mapping must be the first declared port because the current runtime chooses the first declared mapping unless the implicit `7000` fallback applies.
- Backend service ports should be mapped only when they are intentionally exposed through Ploinky routing or needed for host-side diagnostics; otherwise they can remain container-local and be checked by in-container probes.
- If v1 exposes OpenAI-compatible chat completions through Ploinky `/v1/chat/completions/<agent>`, add manifest `endpoints.chatCompletions` handlers per supported model-agent. Translation/reranker agents can expose MCP tools first and should not pretend to be chat-completion models unless their backend implements the contract.

### GPU And Resource Policy

- V1 does not change Ploinky core for GPU passthrough unless explicitly approved later.
- Catalog entries mark `gpuRequired`, recommended VRAM, and CPU-safe status.
- Startup scripts check available memory/CPU/GPU signals where possible and refuse to start obviously unsafe defaults with a clear error.
- Document that high-tier agents require operator GPU/container runtime support outside the current manifest contract.
- A separate follow-up plan should propose a Ploinky `containerSecurity.gpu` or runtime device-passthrough extension. Docker needs `--gpus`; Podman/NVIDIA CDI needs `--device nvidia.com/gpu=all` plus related security options, and neither is modeled by the current manifest contract.

### Dynamic Promotion

- Runtime profiles are logical manager-owned profiles until promoted.
- `promote_agent_profile` writes generated files into the repo checkout as a development operation only.
- Newly promoted first-class agents require Ploinky enable/start or restart; promotion is not hot-add.

## Test Plan

- Validate every catalog file against a JSON schema.
- Unit-test backend selection for all listed models, including transformers-only cases.
- Unit-test the model routing audit so encoder-decoder and reranker models cannot be assigned to generic chat-only runners by accident.
- Unit-test config merge precedence: repo defaults, profile defaults, workspace registry, explicit tool args.
- Unit-test manager vs model-agent MCP tool surfaces.
- Unit-test script generation paths under `.ploinky/data/local-llms/scripts`.
- Smoke-test `ploinky start local-llms-manager <port>` and confirm manager readiness does not wait on no-wait model agents.
- Smoke-test mocked Ollama, llama.cpp, vLLM/SGLang, transformers-seq2seq, reranker, and optional llmster runner flows for list/download/start/stop/status.
- Add an integration smoke with one tiny real model per active backend when feasible.
- Verify default logs redact prompts, payloads, tokens, generated scripts with secrets, and raw model responses.

## Assumptions And Defaults

- The original requested table remains the target catalog, but model compatibility is audited before assigning each model to a backend.
- LM Studio is not a default v1 dependency. It may be added as an experimental llmster runner after a container smoke test.
- Model storage is shared per backend to avoid duplicate multi-GB downloads; per-agent scratch stays isolated.
- Default startup remains light and non-blocking.
- Soul Gateway integration is optional and future-facing; v1 local agents can expose MCP lifecycle tools first, then OpenAI-compatible endpoints where the backend contract is actually supported.
